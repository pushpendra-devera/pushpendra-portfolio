Realtime voice makes a direct client-to-provider connection attractive. It
reduces media latency and avoids routing every audio packet through an
application server. The security problem is that a mobile application cannot
safely contain a long-lived provider key.

## Separate authorization from media

The useful pattern is a small token service:

1. The authenticated mobile client requests a realtime session.
2. The server uses its protected provider key to mint a short-lived credential.
3. The client uses that temporary credential to establish WebRTC directly.
4. The temporary credential expires without exposing the server's long-lived
   secret.

The server stays in the authorization path without becoming the media relay.

## Realtime is one transport, not the whole product

The bilingual voice-agent prototype also separates the primary WebRTC path
from an HTTP and Server-Sent Events fallback composed of transcription,
response generation, and streamed speech. That fallback has higher latency but
is useful when realtime transport is unavailable.

The committed prototype does not yet connect the fallback automatically after
a failed realtime connection, so the architecture is documented as incomplete
rather than presented as seamless failover.

## Interaction state matters too

Push-to-talk is more than toggling a microphone. Assistant playback should be
muted or interrupted when the user begins speaking, otherwise the agent can
record its own output or talk over the user.

Reliable voice systems need three explicit boundaries: server-owned long-lived
credentials, short-lived client authorization, and clear ownership of audio
state during speaking, playback, interruption, and fallback.

Multimodal prototypes often begin with the shortest path to a working result:
put an API key in settings, store it locally, and call the provider directly
from the app. That is acceptable for a controlled experiment if the limitation
is explicit. It is not a production credential model.

## What the prototype proves

ChatGPT Assist combines three different mobile interactions:

- A conversation that retains message history.
- Image generation with results rendered inside the chat experience.
- Device audio recording followed by multipart upload and transcription.

Shared credential state and a reusable API hook keep those screens consistent.
The engineering value is in coordinating navigation, recording permissions,
uploads, loading states, failures, and different response types in one mobile
interface.

## What it does not prove

A key stored in AsyncStorage can be recovered from a compromised device or
application backup. A provider key shipped through a client-controlled request
also gives the backend no reliable place to enforce per-user limits, allowed
models, request validation, or abuse controls.

## The production boundary

A production version should put provider access behind a server-owned API. The
mobile client authenticates to that service; the service validates the request,
applies authorization and rate limits, and either performs the provider call or
mints a narrowly scoped short-lived token where the provider supports one.
Device-side secrets should use OS-backed secure storage, but secure storage is
not a substitute for keeping a long-lived provider credential off the client.

The lesson is not that direct integration is useless. It is that prototype
speed and production security solve different problems, and a portfolio should
state clearly which boundary the implementation currently occupies.
